# 오디오 싱크로나이저 예제

이 예제는 `audio-synchronizer` 컴포넌트를 시연합니다. 여러 녹화본이 같은 오디오를 공유할 때(멀티 카메라 촬영, 동일 스트림의 미러링, 같은 이벤트를 서로 다른 기기로 담은 경우 등) 서로 간의 시간 오프셋을 계산합니다.

컴포넌트는 각 소스를 ffmpeg로 모노 PCM으로 디코딩한 뒤 첫 번째 소스를 기준으로 FFT 기반 상호상관을 수행합니다. 입력마다 하나의 `{offset, confidence}` 항목을 반환하며, 가장 늦게 시작한 소스를 앵커로 잡아 각 오프셋이 해당 소스의 앞부분에서 얼마나 잘라내야 공통 시작점에 도달하는지를 나타내도록 재조정됩니다.

## 개요

`audio-synchronizer` 컴포넌트를 기반으로 한 단일 워크플로우를 제공합니다:

- **Align Recordings**: 녹화본 리스트에 대해 가장 늦게 시작한 녹화본을 앵커로 삼아 녹화본별 오프셋을 계산합니다.

컴포넌트는 비디오와 오디오 소스를 구분 없이 받으며, 디코딩 과정에서 비디오 트랙은 제거됩니다.

## 준비사항

### 사전 요구사항

- model-compose 설치 및 PATH에 등록
- [ffmpeg](https://ffmpeg.org/) 설치 및 PATH에 등록
- `numpy` 설치 (`pip install numpy`)

### 설정

이 예제 디렉토리로 이동합니다:
```bash
cd examples/media-processing/audio-synchronizer
```

ffmpeg가 설치되어 있는지 확인합니다:
```bash
ffmpeg -version
```

## 실행 방법

1. **서비스 시작:**
   ```bash
   model-compose up
   ```

   다음이 시작됩니다:
   - API 엔드포인트: http://localhost:8080/api
   - Web UI: http://localhost:8081

2. **워크플로우 실행:**

   **Web UI 사용:**
   - Web UI 열기: http://localhost:8081
   - 녹화본(오디오 또는 비디오) 업로드
   - "Run Workflow" 클릭

   **CLI 사용:**
   ```bash
   model-compose run --input '{
     "sources": [
       "/path/to/camera-a.mp4",
       "/path/to/camera-b.mp4",
       "/path/to/camera-c.mp4"
     ]
   }'
   ```

   **API 사용:**
   ```bash
   curl -X POST http://localhost:8080/api/workflows/runs \
     -F "sources=@/path/to/camera-a.mp4" \
     -F "sources=@/path/to/camera-b.mp4" \
     -F "sources=@/path/to/camera-c.mp4"
   ```

## 컴포넌트 상세

### 오디오 싱크로나이저 컴포넌트

- **타입**: `audio-synchronizer`
- **드라이버**: `ffmpeg`
- **용도**: 같은 오디오를 공유하는 녹화본들 사이의 시간 오프셋을 ffmpeg 디코딩 PCM에 대한 FFT 상호상관으로 추정합니다.

각 소스는 상호상관 전에 8 kHz 모노 PCM으로 디코딩됩니다. 이 샘플레이트는 음성/음악의 트랜지언트에 필요한 대역폭을 충분히 유지하면서 FFT 비용을 낮게 유지합니다. 상관 피크 주변의 포물선 보간으로 서브샘플 정밀도를 복원하므로, 보고되는 오프셋은 1/8000 s에 제한되지 않습니다.

비디오와 오디오 소스가 모두 허용됩니다. 디코더가 비디오 트랙을 제거하므로 동일 이벤트의 `.mp4`와 `.wav` 녹화본을 별도 전처리 없이 정렬할 수 있습니다.

#### 주요 필드

| 필드 | 타입 | 필수 | 기본값 | 설명 |
|-------|------|----------|---------|-------------|
| `sources` | 미디어 소스 리스트 | 예 | - | 정렬 대상 녹화본. 첫 번째 항목이 상관 기준입니다 |
| `batch_size` | 정수 | 아니오 | 전체 소스 | 병렬로 디코딩할 소스 개수 |

#### 출력

액션은 `sources`와 동일한 순서로 `{offset, confidence}` 항목 리스트를 반환합니다. 오프셋은 가장 늦게 시작한 소스를 앵커로 잡습니다. 앵커 소스는 `offset = 0.0`을 보고하고, 나머지 소스는 각자 시작 부분에서 몇 초를 잘라내야 공통 시작점에 도달하는지를 보고합니다. 따라서 모든 오프셋은 `>= 0`이며 다운스트림 클리퍼에 그대로 넣을 수 있습니다.

| 필드 | 타입 | 설명 |
|-------|------|-------------|
| `offset` | 실수(초) | 이 소스를 가장 늦게 시작한 소스에 맞추기 위해 시작 부분에서 잘라낼 양. 앵커 자신은 `0.0` |
| `confidence` | 실수 0..1 | 상관 기준(첫 번째 소스)에 대한 정규화 피크 상관계수. 1.0에 가까우면 매칭이 깨끗함을, 0에 가까우면 두 녹화본이 같은 오디오를 공유하지 않을 가능성이 큼을 의미 |

세 대의 카메라에 대한 출력 예시 (카메라 A는 상관 기준이지만, 카메라 B가 가장 늦게 시작해 앵커가 되는 경우):

```json
[
  { "offset": 1.2345, "confidence": 1.000 },
  { "offset": 0.0000, "confidence": 0.987 },
  { "offset": 1.7345, "confidence": 0.972 }
]
```

해석: 카메라 B가 가장 늦게 시작해 공통 원점이 됩니다. 카메라 A는 앞부분 1.2345 s, 카메라 C는 앞부분 1.7345 s를 잘라내야 카메라 B와 정렬됩니다.

## 워크플로우 상세

### Align Recordings

**설명**: 임의 개수의 녹화본에 대해 가장 늦게 시작한 녹화본을 앵커로 삼아 오프셋을 계산합니다.

#### 입력 파라미터

| 파라미터 | 타입 | 필수 | 설명 |
|-----------|------|----------|-------------|
| `sources` | 파일 리스트 | 예 | 정렬할 녹화본. 출력에서는 순서가 유지되며, 앵커는 자동으로 선택됩니다 |

#### 출력

| 필드 | 타입 | 설명 |
|-------|------|-------------|
| `offsets` | 리스트 | 소스별 `{offset, confidence}` 항목 하나씩, 입력 순서대로. `offset`은 해당 소스의 앞부분에서 잘라내 공통 시작점에 도달하기까지의 초 단위 값 |

## 팁

- **앵커는 자동 선택**: 가장 늦게 시작한 녹화본이 공통 원점(`offset = 0`)이 되고, 나머지 녹화본은 음이 아닌 헤드 트림 값을 보고합니다. 입력 순서는 반환 리스트의 배열만 결정합니다.
- **오프셋 적용**: 다운스트림 `audio-clipper` 또는 `video-clipper`가 각 소스의 시작 부분에서 `offset` 초를 잘라내면 공통 타임라인에 정렬됩니다 — 부호 확인이나 패딩 단계 필요 없음.
- **첫 번째 소스는 상관 기준이지 앵커가 아님**: 첫 번째 소스는 FFT 단계의 상관 기준으로 사용되어 confidence가 항상 `1.0`으로 보고됩니다. 이것이 타임라인 앵커라는 뜻은 아닙니다.
- **Confidence 임계값**: 실제 매칭은 대개 ~0.5 이상에서 형성됩니다. ~0.2 미만이면 두 녹화본이 같은 오디오를 공유하지 않을 가능성이 크므로 오프셋을 신뢰하지 마세요.
- **오디오와 비디오 혼합**: 비디오 컨테이너는 자동으로 오디오로 디코딩되므로, `.mp4`, `.mov`, `.wav`, `.mp3` 파일을 하나의 `sources` 리스트에 자유롭게 섞을 수 있습니다.
- **길이 차이**: 녹화본 길이가 같을 필요는 없습니다. 상호상관은 두 신호 사이의 모든 lag를 스캔하므로, 30분 녹화본을 이벤트 중간에 있는 5분 녹화본에 정렬할 수도 있습니다.
- **클록 드리프트**: 컴포넌트는 소스당 하나의 오프셋만 보고하며, 각 녹화 클록이 동일한 속도로 흐른다고 가정합니다. 저가 하드웨어의 장시간 녹화는 시간당 수십 밀리초 드리프트가 발생할 수 있으므로, 드리프트가 중요하다면 짧은 세그먼트로 분할해 각각 정렬하세요.
- **정적 구간과 반복 패턴**: 기준 신호의 어떤 구간이 특징이 없다면(긴 정적, 반복 비트) 상관 피크가 잘못된 사본에 붙을 수 있습니다. 박수, 문 닫는 소리, 발화어 같은 뚜렷한 트랜지언트가 있는 구간을 정렬하세요.

## 문제 해결

### 자주 발생하는 문제

1. **ffmpeg를 찾을 수 없음**: ffmpeg가 설치되어 있고 `PATH`에 등록되어 있는지 확인하세요.
2. **`numpy` 없음**: 싱크로나이저는 FFT 상관에 numpy를 사용합니다. `pip install numpy`로 설치하세요.
3. **모든 confidence가 낮음(< 0.2)**: 녹화본들이 같은 오디오를 공유하지 않거나 한쪽이 무음일 가능성이 큽니다. 오프셋을 신뢰하기 전에 귀로 소스를 먼저 확인하세요.
4. **의도치 않은 소스가 offset = 0을 보고함**: 그 소스가 가장 늦게 시작한 소스, 즉 공통 시작 앵커라는 뜻입니다. 다른 소스가 앵커여야 한다면 입력을 재정렬하거나(그 소스가 실제로 가장 늦게 시작해야 숫자가 의미 있음) 외부에서 정렬하세요.
5. **Confidence는 높은데 오프셋이 초 단위로 어긋남**: 반복 패턴(메트로놈, 반복 징글)이 잘못된 lag에서 강한 이차 피크를 만들 수 있습니다. 고유한 트랜지언트가 포함된 구간을 넣거나, 변화가 많은 구간으로 크롭하세요.
6. **장시간 녹화가 느리게 느껴짐**: 각 소스는 상관 전에 처음부터 끝까지 디코딩됩니다. 몇 시간짜리 파일이라면 실제 정렬이 필요한 구간으로 미리 잘라내세요 — 대개 공유 오디오 1분이면 충분합니다.
