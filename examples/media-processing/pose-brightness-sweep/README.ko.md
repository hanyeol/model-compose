# 포즈 검출 × 밝기 스윕 예제

입력 이미지 한 장을 받아 0–255 ITU-R BT.601 루마 스케일상의 절대 밝기 목표 5단계로 정규화하고, 각 변형본에 YOLOv8-pose를 돌린 뒤 5장의 포즈 오버레이 이미지를 나란히 반환하는 워크플로우 예제입니다. 이 입력에 대해 검출기가 어느 밝기 대역을 가장 선호하는지 눈으로 바로 비교할 수 있습니다.

> **라이선스 주의**: 이 예제는 Ultralytics의 YOLOv8-pose 가중치를 자동 다운로드하며, 이 가중치는 **AGPL-3.0**으로 배포됩니다. 개인 사용, 연구, 오픈소스 데모는 문제없습니다. 상업 사용의 경우에는 AGPL-3.0을 준수(전체 시스템 소스 공개)하거나 Ultralytics Enterprise License를 취득해야 합니다 — [ultralytics.com/license](https://www.ultralytics.com/license) 참고.

## 개요

입력 이미지를 주면 워크플로우는 목표 루마 대역별로 하나씩, 총 5장의 포즈 오버레이 이미지를 반환합니다 (기본값: `50`, `90`, `130`, `170`, `210`). 각 필드는 완전히 렌더링된 이미지(밝기 조정 + 스켈레톤 오버레이)이며, 이름(`luma_050` … `luma_210`)으로 지정해서 사용할 수 있습니다.

전략:

1. **업로드를 스풀링하고 두 단계로 fan-out.** 첫 번째 `fan-out` 작업은 `spool: true` 모드로 동작 — 1회성 업로드를 임시 파일에 한 번만 저장하고, 두 브랜치(`for-measure`, `for-sweep`)에 각각 파일 기반 이미지 리소스를 넘겨줍니다. 이 리소스는 복사 가능하므로, 두 번째 `fan-out`은 저렴한 `copy(N)` 경로로 입력을 분할합니다 (두 번째 임시 파일 없음). 이로써 스윕 대상마다 독립 핸들이 하나씩 생깁니다. 두 단계로 나눈 이유는 관심사 분리를 위함입니다: 분석기는 자기 브랜치를 즉시 소진할 수 있고, 스윕 파이프라인은 `measure` 완료를 기다리면서도 분석기를 정체시키지 않습니다 (그 시점에는 스풀 파일이 이미 완전히 기록되어 있음).
2. **소스 루마를 한 번만 측정** — `image-analyzer` (`analyze-brightness` 메트릭). 0–255 BT.601 루마 스케일의 `mean_brightness`를 반환하며, 이 값은 모든 스윕 이터레이션이 목표별 계수를 도출할 때 쓰는 분모입니다.
3. **Fan out** — 최상위 `for-each` 작업이 목표 루마 리스트를 순회하며, 각 목표를 자기 몫의 두 번째 fan-out 브랜치와 짝지어 `{luma, image}` 아이템으로 만듭니다. 각 이터레이션은 인라인 `pipeline`을 독립적으로 실행하며, `batch_size: 5` 덕분에 CPU 측 스텝이 겹쳐서 돌아갑니다.
4. **각 이터레이션 내부에서** — 작은 Python 셸 작업으로 `factor = target / original`을 계산하고, `image-processor adjust-brightness`로 적용한 뒤, YOLOv8-pose를 실행 (`return_skeleton_image: true`는 포즈별로 소스 해상도의 투명 배경 스켈레톤 PNG를 반환), 마지막으로 `image-processor merge`로 모든 스켈레톤을 밝기 조정된 이미지 위에 알파 합성합니다.
5. **결과 투영** — 최상위 워크플로우의 `output:` 블록이 각 이터레이션을 위치 인덱스(`jobs.sweep.output[0]` … `[4]`)로 골라 그 `pose_overlay_image`를 최상위 `luma_NNN` 필드로 노출합니다. Web UI는 대역별로 이미지 카드를 하나씩 렌더링합니다. `for-each`는 입력 순서를 보존하므로 인덱스 `N`은 항상 스윕 입력 리스트의 N번째 항목에 대응합니다.

### 왜 절대 루마인가 (raw multiplier가 아니라)

Raw multiplier 스윕(`0.5×`, `1.0×`, `2.0×`, …)은 입력의 원래 밝기에 따라 도달하는 절대 밝기 대역이 달라집니다 — 어두운 사진에 대한 2× 시프트는 밝은 사진에 대한 2× 시프트와 완전히 다른 곳에 착지합니다. 절대 루마를 목표로 하면 소스 노출이 정규화되므로, 5개 대역(`50, 90, 130, 170, 210`)은 어떤 입력에 대해서도 동일한 5개 대역입니다. 다른 사진들 사이의 결과 비교가 의미를 가집니다.

트레이드오프: 밝기 조정은 여전히 PIL의 `ImageEnhance.Brightness`(0/255에서 클리핑되는 선형 배수)를 사용합니다. 그래서 매우 어두운 소스를 목표 210까지 올리면 하이라이트 클리핑 때문에 210보다 약간 낮게 착지할 수 있습니다. "검출기가 어느 대역을 좋아하는지" 실험용으로는 충분하지만, 포토메트릭 정규화용으로는 부족합니다.

### 왜 앞단에서 한 번만 측정하는가 (각 이터레이션 안이 아니라)

소스 루마는 5번의 이터레이션 내내 변하지 않으므로, 같은 픽셀을 5번 재분석하는 것은 CPU만 태울 뿐입니다. 외부 워크플로우(`measure` 작업)에서 측정하면 fan-out 전에 한 번만 일어나며, 파생된 값은 각 이터레이션의 파이프라인에 스칼라 `original_luma` 입력으로 전달됩니다.

### 왜 인라인 파이프라인인가 (서브워크플로우가 아니라)

목표별 작업은 4개의 순차 스텝입니다 (factor 계산 → 밝기 조정 → 검출 → 오버레이). `for-each`는 어떤 인라인 작업이든 `do:` 본문으로 실행할 수 있고, `pipeline` 작업은 암묵적인 `${output}` → 다음 `${input}` 연결로 스텝들을 체이닝합니다 — 그래서 네 단계 전체가 `for-each` 안에 직접 살 수 있고, 별도의 워크플로우 정의가 필요 없습니다. 트레이드오프는 스코프입니다: 파이프라인 스텝들은 파이프라인 자신의 `${input}`과 이전 스텝의 `${output}`만 볼 수 있고, 바깥쪽 스코프(예: 감싸는 `${item}`)에는 접근할 수 없습니다. 그래서 파이프라인의 최상위 `input:` 블록에 스텝들이 필요한 모든 것(목표 루마, 소스 이미지 브랜치, 소스 루마, 임계값)을 하나의 dict로 앞에서 담아두고, 각 스텝의 `output:` 매핑이 실행 상태(factor, 밝기 조정된 이미지, 포즈들)를 다음 스텝을 위해 다시 포장합니다.

### 왜 factor 계산을 Python 셸 작업으로 하는가

model-compose의 변수 바인딩 DSL은 값을 렌더링하고 타입 변환은 하지만, 산술 연산은 하지 않습니다. `target / original_luma`를 계산하려면 셸로 나가야 합니다. 두 값을 `argv`로 넘기는 한 줄짜리 `python3 -c` 명령이 가장 작은 우회로입니다. 셸 스텝의 stdout은 평범한 float 문자열이며, 파이프라인의 `output:` 매핑이 `${output as number}`로 강제 변환한 뒤 밝기 조정 스텝에 넘겨줍니다.

## 준비

### 요구사항

- model-compose가 설치되어 PATH에서 사용 가능
- YOLO 포즈 검출과 이미지 분석용 Python 의존성:
  ```bash
  pip install ultralytics numpy
  ```
- YOLOv8n-pose 가중치는 첫 실행 시 model-compose의 모델 캐시로 자동 다운로드됩니다.

### 설정

1. 예제 디렉터리로 이동:
   ```bash
   cd examples/media-processing/pose-brightness-sweep
   ```

2. 눈에 보이는 사람이 적어도 한 명 있는 이미지를 준비합니다.

## 실행 방법

1. **서비스 시작:**
   ```bash
   model-compose up
   ```

2. **워크플로우 실행:**

   **Web UI 사용:**
   - Web UI 열기: http://localhost:8081
   - 이미지 업로드, 필요 시 `min_confidence` / `max_pose_count` 오버라이드
   - "Run Workflow" 클릭
   - 응답에는 5개의 이미지 필드(`luma_050` … `luma_210`)가 담김 — 밝기 대역별로 카드 하나씩, 밝기 조정된 이미지 위에 검출된 스켈레톤이 그려진 모습.

   **API 사용:**
   ```bash
   curl -X POST http://localhost:8080/api/workflows/runs \
     -F 'input={"min_confidence": 0.4, "max_pose_count": 5};type=application/json' \
     -F 'image=@./person.jpg'
   ```

   **CLI 사용:**
   ```bash
   model-compose run --input '{
     "image": "./person.jpg",
     "min_confidence": 0.4,
     "max_pose_count": 5
   }'
   ```

## 입력 파라미터

| 파라미터 | 타입 | 필수 | 기본값 | 설명 |
|---------|------|------|--------|------|
| `image` | image (file) | 예 | - | 밝기 스윕할 입력 이미지 |
| `min_confidence` | number | 아니오 | `0.4` | 포즈 검출 최소 신뢰도 (0.0 – 1.0). 모든 밝기 레벨에서 특정 사람이 놓쳐지면 낮춰봅니다 (예: `0.25`) |
| `max_pose_count` | integer | 아니오 | `5` | 이미지당 반환할 최대 포즈 개수 |

## 출력 형태

각 목표 밝기 대역은 자기 이름의 최상위 이미지 필드 `luma_NNN`로 투영됩니다 (`NNN`은 0–255 스케일의 목표 평균 루마, 0으로 채움). 이 평평한 형태 덕분에 Web UI가 대역별로 이미지 카드를 하나씩 나란히 렌더링합니다.

```json
{
  "luma_050": "<image PNG>",
  "luma_090": "<image PNG>",
  "luma_130": "<image PNG>",
  "luma_170": "<image PNG>",
  "luma_210": "<image PNG>"
}
```

스켈레톤이 이미지 속 사람과 가장 깔끔하게 맞아떨어지는 대역이 이 입력에 대한 검출기의 노출 스위트 스팟입니다. 하부 포즈 데이터(점수, 바운딩 박스)나 오버레이 전의 밝기 조정된 이미지가 필요하다면 파이프라인 출력에서 승격시키세요 — 각 이터레이션은 전체 레코드 `{target_luma, applied_factor, poses, brightened_image, pose_overlay_image}`를 반환합니다. 최상위 워크플로우의 `output:` 블록은 UI를 깔끔하게 유지하려고 현재 `pose_overlay_image`만 투영하지만, 파이프라인 스텝을 건드리지 않고 필드를 더 추가할 수 있습니다.

> **참고**: `sweep` 작업의 목표 루마 리스트를 바꾸면, 워크플로우 `output:` 블록의 필드 이름도 맞춰서 바꿔야 합니다 — 필드 이름은 정적 YAML이지, 런타임에 스윕 값에서 파생되는 것이 아닙니다.

## 컴포넌트 상세

### 이미지 분석기 (`image-analyzer`)
- **타입**: `image-analyzer`
- **드라이버**: `native`
- **기능**: 소스 이미지에 대해 `analyze-brightness`를 실행. 상류 `fan-out` 작업의 `for-measure` 브랜치를 스윕 이터레이션들과 병렬로 소비. `mean_brightness`(BT.601 루마의 산술 평균, 0–255)와 `min/max/std_brightness`, 차원을 반환. 여기서는 `mean_brightness`만 사용 — 목표별 계수의 분모로.

### Factor 계산기 (`factor-calc`)
- **타입**: `shell`
- **기능**: `target / original`(소스가 완전 검정이면 `1.0`)을 출력하는 한 줄짜리 Python 스크립트를 실행. Stdout은 밝기 조정 스텝이 `as number`로 소비. 파이프라인에서 산술이 일어나는 유일한 지점 — 나머지는 순수 변수 바인딩.

### 이미지 프로세서 (`image-processor`)
- **타입**: `image-processor`
- **드라이버**: `native`
- **기능**: 두 개의 액션을 노출. `adjust-brightness`는 픽셀 강도를 `factor`로 곱함 (PIL `ImageEnhance.Brightness`, 0/255 클리핑되는 선형 배수). `merge`는 같은 크기의 이미지 리스트를 한 캔버스에 알파 합성 — 여기서는 스켈레톤 PNG를 각 밝기 조정된 이미지 위에 쌓는 데 사용.

### 포즈 검출기 (`pose-detector`)
- **타입**: `model` — `pose-detection` 태스크
- **드라이버**: `custom`
- **패밀리**: `yolo` (`yolov8n-pose.pt` 가중치)
- **기능**: 한 이미지에서 최대 `max_pose_count`개의 포즈를 검출하고, 각 포즈마다 투명 배경의 풀 해상도 스켈레톤 PNG를 렌더링(`return_skeleton_image: true`). 키포인트 배열은 억제(`return_keypoints: false`) — 오버레이 파이프라인은 미리 렌더링된 스켈레톤 이미지만 필요하므로. `max_concurrent_count: 1`은 추론을 직렬화하여, 외부 `for-each`가 5개 이터레이션을 한 번에 fan-out하더라도 GPU 메모리가 경계 내에 머물게 합니다.

## 노트와 튜닝

- **비용**: 목표 대역당 포즈 검출 1회. 기본 5-대역 스윕에서 벽시계 시간은 대략 단일 포즈 검출 호출의 5배 (동시 CPU 작업이 겹쳐지는 만큼 차감). 정확도가 필요하면 `yolov8s/m/l/x-pose.pt`로 교체 — 비례하여 비용도 증가.
- **스윕 범위**: 기본 `[50, 90, 130, 170, 210]`은 8비트 루마 스케일에서 깊은 그림자 → 중간 → 하이라이트를 커버. `128`이 정확한 중간점. `~40` 이하는 사실상 뭉개진 그림자, `~215` 이상은 하이라이트 블로우아웃. 기본값이 유스케이스에 너무 성기다면 `sweep` 작업의 리스트를 편집해서 더 좁은 대역에 집중.
- **모든 대역에서 포즈 놓침**: 모든 변형에서 포즈가 안 보이면, 검출기가 애초에 사람을 못 본 것 — 밝기가 문제라고 단정하기 전에 `min_confidence`를 낮추거나(예: `0.25`) 더 큰 YOLO 가중치로 교체.
- **오버레이의 베이스 이미지**: 특정 목표에서 포즈가 0개 검출되면, `pose_overlay_image`는 밝기 조정된 이미지와 동일합니다 (merge가 그냥 베이스를 반환). 의도된 동작 — 5장의 출력 카드가 시각적으로 정렬되어 있어 갭 없이 넘겨볼 수 있게 하기 위함.
- **절대 루마의 한계**: 밝기 액션은 클리핑되는 선형 배수라서, 극단적 시프트(매우 어두운 입력 → 높은 목표, 또는 매우 밝은 입력 → 낮은 목표)는 목표를 벗어나서 착지합니다. 스윕 시각화보다 정확한 포토메트릭 정규화가 더 중요하다면 감마 기반 톤 맵을 사용하세요 — `image-processor`는 현재 이를 노출하지 않으므로 코어에 추가해야 합니다.
